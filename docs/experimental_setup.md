# Experimental Setup and Reproducibility Guide

**Status:** Planned protocol for live experiments. No live experiments have been run yet; current results in this repository come from simulation (see the README). This document describes the intended setup and will be updated as the live harness is built and tested.

## Hardware Configuration (planned)

**Local reproduction environment (Docker Compose):**
- CPU: 4+ cores recommended
- RAM: 8 GB minimum (16 GB recommended)
- Storage: 20 GB free (checkpoint directories grow during runs)

A multi-node cluster configuration will be documented when cluster experiments are run.

## Software Versions (planned)

| Component | Version |
|-----------|---------|
| Apache Spark | 3.5.0 |
| Apache Kafka | 3.6.0 |
| Python | 3.10 |
| Java | 11 |

Exact versions used in each run will be recorded in that run's output.

## Data Generation

Synthetic IoT sensor events generated by `src/kafka_producer.py`:
- Schema: `{device_id: str, timestamp: long, value: float, sequence_number: int}`
- Target rate: 1,000 messages/second
- Planned volume: 1,000,000 messages per run
- `sequence_number` provides a unique ID per record for duplicate detection

## Checkpoint Strategy Definitions

Spark Structured Streaming always records source offsets and batch commits in write-ahead logs inside the checkpoint directory. There is no separate on/off write-ahead-log setting for Structured Streaming; `spark.streaming.receiver.writeAheadLog.enable` applies only to the older DStreams API. The strategies below therefore differ in trigger interval and state-store checkpointing, not in whether a write-ahead log exists.

### Strategy A: Short trigger interval
```python
.writeStream \
  .option("checkpointLocation", "/checkpoints/strategy_a") \
  .trigger(processingTime='1 second') \
  .start()
```

### Strategy B: Long trigger interval
```python
.writeStream \
  .option("checkpointLocation", "/checkpoints/strategy_b") \
  .trigger(processingTime='30 seconds') \
  .start()
```

### Strategy C: RocksDB state store with changelog checkpointing
```python
spark.conf.set(
    "spark.sql.streaming.stateStore.providerClass",
    "org.apache.spark.sql.execution.streaming.state.RocksDBStateStoreProvider")
spark.conf.set(
    "spark.sql.streaming.stateStore.rocksdb.changelogCheckpointing.enabled", "true")

.writeStream \
  .option("checkpointLocation", "/checkpoints/strategy_c") \
  .trigger(processingTime='10 seconds') \
  .start()
```
Requires Spark 3.4 or later. In the simulation code this strategy is labeled "10s WAL"; that label will be updated to match this definition.

### ACS (Adaptive Checkpoint Selection)
A running Structured Streaming query cannot change its trigger interval. A live ACS implementation will need to stop and restart the query from its checkpoint with a new trigger, or use a custom trigger. The design is open.

## Failure Injection Protocol (planned)

Each run will follow this sequence:
1. Start Kafka and Zookeeper
2. Start the Spark pipeline with the chosen strategy
3. Wait for steady state (30 seconds after the first micro-batch)
4. Inject the failure
5. Measure recovery time: from failure injection until throughput returns within 10% of the pre-failure baseline
6. Continue until all records are processed
7. Compute duplicate and missing-record counts from `sequence_number` in the sink output

### Failure types
| Type | Planned method |
|------|----------------|
| Executor/node failure | `docker kill` on a worker container |
| Driver failure | `docker kill` on the driver container |
| Checkpoint corruption | Overwrite part of the latest offset file in the checkpoint directory |
| Network partition | `tc netem loss 100%` on the worker container for a fixed period |

`src/failure_simulator.py` is intended to wrap these operations; its interface will be finalized with the runner.

## Planned Output per Run

Each run is intended to produce a JSON file containing:
- `throughput_rps`: records processed per second (mean over the run)
- `recovery_latency_ms`: time from failure injection to throughput recovery
- `duplicate_count`: records delivered more than once
- `missing_count`: records never delivered
- `checkpoint_size_bytes`: size of the checkpoint directory at failure time
- Versions, configuration, and timestamps for the run

Logs and checkpoint directory snapshots from before and after injection will be preserved alongside each run's output.

## Reproducibility Notes

- Fixed random seeds will be used for data generation.
- Kafka topics will be recreated fresh before each run.
- Checkpoint directories will be wiped between runs.
- The number of repetitions per configuration will be set once the harness is working, and reported with each result.
