# Fault Tolerance in Spark Structured Streaming and Flink: Live Measurements, a Simulation Study, and an Adaptive Checkpointing Prototype

**Author:** Rajshekar Medipally
**GitHub:** [github.com/rmedipallycic](https://github.com/rmedipallycic)
**Status:** Paper draft: [*Does Adaptive Checkpointing Help Spark Structured Streaming? A Fault-Injection Study of Replay, Recovery and Latency*](paper/main.pdf). Measured: 84 trials of delivery under driver kill and checkpoint corruption (below), and 126 trials comparing a live adaptive controller (ACS) with fixed trigger intervals (`experiments/live_acs/`, `experiments/live_acs2/`). ## Research Question

> How do fault-tolerance mechanisms in Apache Spark Structured Streaming and Apache Flink differ in throughput, recovery latency, and data correctness under failure — and what are the implications for ML feature pipelines?

---

## Adaptive Checkpoint Selection (ACS): design and live result

Fixed checkpoint intervals trade overhead against recovery cost. A long interval (e.g., 30s) is cheap during stable operation but increases replay and duplicate exposure after a failure. A short interval (e.g., 1s) reduces replay but adds constant overhead.

ACS is a proposed feedback controller that adjusts the checkpoint interval using three pipeline health signals:

- **Throughput variance** — coefficient of variation of recent throughput samples
- **Error pressure** — exceptions per 1,000 records in the current window
- **Failure recency** — exponential decay signal since the last detected failure

Every 5 seconds, ACS computes a risk score in [0, 1]:

- **Risk > 0.45** → tighten the interval by 30%
- **4 consecutive stable windows** → relax the interval by 20%
- **Bounds:** 2s ≤ interval ≤ 45s

Weights (0.4 / 0.3 / 0.3) and thresholds were chosen heuristically and were not tuned on measured runs.

**Live implementation** ([`live/acs.py`](live/acs.py)). A running Structured Streaming query cannot change its trigger interval, so the controller waits until the query is between batches, stops it, and starts it again on the same checkpoint in the same Spark session. Error pressure, which is always 0 in a healthy live pipeline when counted as exceptions, is measured instead as the fraction of batches that ran longer than the trigger interval.

**What the live measurements showed** (details in the [paper](paper/main.pdf) and [below](#live-acs-comparison-measured-results-local)):
- The rule as specified (**v1**) cannot react to any single signal: instability alone reaches at most 0.4, a recent failure at most 0.38, against a threshold of 0.45, and the interval relaxes during bursts. A revision (**v2**: tighten above 0.30, stable below 0.15) was fixed before any measured run, and both were measured.
- Interval switches were cheap (median 0.54 s) and caused no duplicates in 320 switches.
- On paired workloads and failures, a **fixed interval at ACS's own mean matched or beat it**. In micro-batch Spark a crash rarely forces a batch to be redone, and recovery does not depend on the interval, so the interval trades latency against checkpoint overhead, and a fixed value chosen for the latency target serves that directly.

> Implementations: live [`live/acs.py`](live/acs.py); simulation [`src/adaptive_checkpoint.py`](src/adaptive_checkpoint.py)

## Simulation Results

### ACS vs. fixed-interval Spark strategies (simulated)

Source: `src/adaptive_checkpoint.py`, 480 simulated trials (4 strategies × 4 scenarios × 30 trials). Summary: `experiments/experiments/adaptive/adaptive_summary.csv`.

| Strategy | Baseline throughput | Recovery, driver failure | Dup rate, checkpoint corruption | Dup rate, driver failure | Dup rate, node failure |
|----------|--------------------:|-------------------------:|--------------------------------:|-------------------------:|-----------------------:|
| Strategy A (1s fixed) | 50,049 rec/s | 5,061 ms | 0.183% | 0.188% | 0.177% |
| Strategy B (30s fixed) | 49,909 rec/s | 25,334 ms | 2.961% | 4.432% | 5.414% |
| Strategy C (10s WAL) | 49,951 rec/s | 4,993 ms | 0.207% | 0.102% | 0.218% |
| ACS (proposed) | 50,010 rec/s | 12,264 ms | 0.036% | 0.066% | 0.009% |

**Interpretation — model behavior, not system measurements:**

- **Throughput:** Baseline throughput is nearly identical across strategies (~50,000 rec/s) because the simulator does not model checkpoint overhead differences. These results say nothing about the throughput cost of ACS.
- **Recovery latency:** Recovery time in the simulator equals the time since the last checkpoint, evaluated on a 5-second simulation tick. This is why Strategy A (1s interval) shows ~5,000 ms rather than ~1,000 ms. ACS shows longer driver-failure recovery than Strategies A and C in this model.
- **Duplicate rate:** ACS has the lowest duplicate rate in all three failure scenarios. In this simulator, ACS's duplicate rate is computed from its replay window, while the fixed strategies use constant duplicate-rate parameters. The advantage therefore follows from how the model was written. It illustrates the mechanism ACS is designed to exploit; live experiments are needed to test whether it exists in real Spark.

Note: `experiments/summary.csv` comes from a separately parameterized simulator (`run_simulation.py`). Its values for Strategies A, B, and C differ from the table above.

### Spark vs. Flink (simulated)

Source: `experiments/run_simulation.py` (360 Spark trials) and the Flink simulation (360 trials).

- **Baseline throughput:** Flink F1 54,759 rec/s vs. Spark B 51,268 rec/s, a 6.8% difference in the simulation.
- **Duplicates:** The Flink simulation produces zero duplicates and zero data loss **by construction**. Its model does not generate duplicates under any scenario. This reflects the documented design of Flink's Chandy-Lamport barrier snapshots. It is **not** an experimental finding about Flink.

### Simulation statistics

Welch's t-tests recalculated independently from the raw simulation data:

| Comparison | Welch's t | p-value | Cohen's d |
|------------|----------:|--------:|----------:|
| Spark B vs. ACS (duplicate rate) | 28.94 | < 0.001 | 7.47 |
| Spark A vs. ACS (duplicate rate) | 27.36 | < 0.001 | 7.06 |
| Spark C vs. ACS (duplicate rate) | 30.66 | < 0.001 | 7.92 |
| Flink F1 vs. Spark B (throughput) | 5.90 | < 0.001 | 1.52 |

These statistics describe separation between **simulated distributions whose means were set by the model**. They do not establish differences between real systems.

## Systems Modeled

| System | Mechanism | Intended correctness target |
|--------|-----------|-----------------------------|
| Spark A | Micro-batch checkpoint, 1s | Exactly-once |
| Spark B | Micro-batch checkpoint, 30s | Exactly-once |
| Spark C | Checkpoint with write-ahead log, 10s | Exactly-once |
| ACS | Risk-based dynamic interval, 2–45s | Exactly-once |
| Flink F1 | Aligned barrier snapshots, 10s | Exactly-once |
| Flink F2 | Unaligned barrier snapshots, 10s | Exactly-once |
| Flink F3 | Incremental RocksDB snapshots, 30s | Exactly-once |

Failure scenarios modeled: executor failure, driver/JobManager failure, checkpoint corruption, network partition.

## Live Experiments: Measured Results (local)

**Setup.** Spark Structured Streaming 3.5.3 (PySpark, `local[2]`), Java 17, reading a 4-partition Kafka topic (Confluent 7.5.0 in Docker Compose, one broker) on one laptop under WSL2 (Intel Core i5-1335U, 8 GB given to WSL). Each trial produces 36,000 records with sequence numbers at 300 records/s through an idempotent producer, so that any duplicate comes from Spark. Strategies: **A** (1 s trigger) and **B** (30 s trigger). Sinks: Spark's **file** sink (exactly-once through its `_spark_metadata` log) and a **foreachBatch** sink that appends each micro-batch as a new file (at-least-once). Failures: **driver_failure** (SIGKILL of the whole Spark process, then restart from the checkpoint) and **checkpoint_corruption** (SIGKILL, then overwrite part of the latest `offsets/` file, then restart). Kill times are spread across the trigger interval. 10 trials per strategy, failure and sink, plus one no-failure baseline each: **84 trials**, code commits `4a2dfe3` (strategy A) and `5607d08` (strategy B).

**Results** (generated by `live/analyze.py` into `experiments/live/summary.md`):

| Strategy | Failure | Sink | Trials | Outcomes | Trials with duplicates | Duplicate rows (median, max) | Trials missing records | Recovery s, median (min-max) |
|---|---|---|---|---|---|---|---|---|
| A | checkpoint_corruption | file | 10 | restart_failed 10 | 0/10 | 0, 0 | 0/0 (completed trials) | - |
| A | checkpoint_corruption | foreachbatch | 10 | restart_failed 10 | 0/10 | 0, 0 | 0/0 (completed trials) | - |
| A | driver_failure | file | 10 | ok 10 | 0/10 | 0, 0 | 0/10 (completed trials) | 11.0 (9.5-15.5) |
| A | driver_failure | foreachbatch | 10 | ok 10 | 1/10 | 0, 300 | 0/10 (completed trials) | 10.0 (9.5-28.6) |
| A | none | file | 1 | ok 1 | 0/1 | 0, 0 | 0/1 (completed trials) | - |
| A | none | foreachbatch | 1 | ok 1 | 0/1 | 0, 0 | 0/1 (completed trials) | - |
| B | checkpoint_corruption | file | 10 | restart_failed 10 | 0/10 | 0, 0 | 0/0 (completed trials) | - |
| B | checkpoint_corruption | foreachbatch | 10 | restart_failed 10 | 0/10 | 0, 0 | 0/0 (completed trials) | - |
| B | driver_failure | file | 10 | ok 10 | 0/10 | 0, 0 | 0/10 (completed trials) | 14.8 (12.0-17.0) |
| B | driver_failure | foreachbatch | 10 | ok 10 | 0/10 | 0, 0 | 0/10 (completed trials) | 13.3 (11.0-20.5) |
| B | none | file | 1 | ok 1 | 0/1 | 0, 0 | 0/1 (completed trials) | - |
| B | none | foreachbatch | 1 | ok 1 | 0/1 | 0, 0 | 0/1 (completed trials) | - |

84 measured trials, code commit(s) 4a2dfe3, 5607d08. Missing records are counted only for trials whose restart succeeded; a failed restart stops the pipeline, which is reported as its outcome.

**What the measurements show**

1. **The exactly-once file sink delivered exactly once.** In all 20 driver kills (both strategies), the committed output had every record once: 0 duplicates and 0 missing records out of 36,000. Even the raw output files, including any not committed, contained no duplicates.
2. **The at-least-once sink duplicated a batch once in 20 kills.** One strategy-A trial (`..._A_driver_failure_foreachbatch_t03`) received 300 records twice, exactly one 1-second micro-batch at 300 records/s, replayed after the restart. The other 19 had none. A duplicate needs the kill to land between a batch's write and its commit; with a 30 s trigger that window is a small part of each interval, and none of the 10 strategy-B kills hit it.
3. **A corrupted offset log stopped the pipeline in 40 of 40 trials.** Spark refused to restart (`MalformedInputException` in every log, exit code 3) rather than continue silently. No duplicates or silent losses were produced; the records after the failure were simply not processed until an operator intervenes.
4. **Recovery after a driver kill took 9.5–28.6 s** (median 10.5 s for strategy A, 14.3 s for strategy B, over 20 trials each), measured from the kill to the first micro-batch committed after restart. In every trial, most of that time (median 67%, at least 57%, from the timestamps in each `spark.log`) passed before the restarted query was running, that is, in JVM and Spark start-up; the rest was the first batch after the restart.

**Measured versus the earlier simulation.** The simulation (below) assumed constant duplicate rates for every failure. The live runs differ in kind, not just degree:

| | Simulated (`adaptive_checkpoint.py`) | Measured (this section) |
|---|---|---|
| Checkpoint corruption | duplicates: 0.18% (A), 2.96% (B) | restart fails in 40/40 trials; no duplicates; pipeline stops |
| Driver failure, duplicates | 0.19% (A), 4.43% (B) | file sink 0 in 20/20; foreachBatch 300 rows in 1 of 20 trials |
| Driver failure, recovery | 5.1 s (A), 25.3 s (B) | median 10.5 s (A), 14.3 s (B) |

The simulation did not model a sink, so its duplicate rates have no measured counterpart for the file sink, which by design admits none.

**Scope and limits.** One machine, local mode, one Kafka broker, a low rate (300 records/s), and one kind of corruption (overwriting part of the latest offset file); executor-only failures, network loss and multi-node clusters are not covered. Ten trials per configuration show what happens and roughly how often, not precise rates; in particular, the 1-in-20 duplicate event says only that replay duplicates occur under the at-least-once sink, not how often. Recovery times include JVM and Spark start-up on a laptop.

**Provenance.** A first attempt at strategy B was invalidated by a full `/tmp` (scratch files of SIGKILLed Spark processes); those 42 trials are kept with an explanation in [`experiments/live_excluded/`](experiments/live_excluded/README.md) and are not used. Strategy B was re-run after the fix.

|---|---|---|---|---|
| A (1 s) | 0.84 | 8.75 | 82 | 10.5 |

### How the live runner works

The live runner is in [`live/`](live/). It does not use `src/pipeline.py`, whose windowed counts cannot show which records were duplicated or lost; [`live/stream_job.py`](live/stream_job.py) keeps every record's sequence number instead.

One trial ([`live/run_trial.py`](live/run_trial.py)):
1. Create a fresh Kafka topic and produce N records with sequence numbers 0..N-1 at a fixed rate, using an idempotent producer so that any duplicates measured come from Spark.
2. Start the Spark job (local mode) reading the topic from the earliest offset.
3. After the first committed output, inject the failure: **driver_failure** (SIGKILL the Spark process group) or **checkpoint_corruption** (SIGKILL, then overwrite part of the latest `offsets/` file). The kill time is spread across the trigger interval over trials.
4. Restart from the same checkpoint, record when the first micro-batch commits (recovery latency), wait until output stops changing, and stop the query gracefully.
5. Count duplicated and missing records in the committed output, and separately in all raw output files.
6. Keep a per-trial `trial.json` (configuration, git commit, versions, timings, counts, duplicated and missing sequence numbers), the Spark log, and checkpoint snapshots before restart and after corruption.

Two sinks are measured because they answer different questions: Spark's **file** sink is exactly-once through its `_spark_metadata` commit log, while the **foreachbatch** sink appends each micro-batch as a new file and is at-least-once. Strategies: A (1 s trigger) and B (30 s trigger).

Before the measured runs, the runner was exercised end to end with a file-based test source and then with short smoke trials against Kafka; smoke trials are written to `experiments/live_smoke/` (not committed) and are not results.

```bash
# inside WSL2 Ubuntu, with Docker Desktop running
bash live/setup_wsl.sh                  # Java 17, Python 3.11 env, PySpark 3.5.3, Kafka up
source ~/venv-live/bin/activate
bash live/run_grid.sh smoke             # 3 short trials against Kafka
TRIALS=10 bash live/run_grid.sh         # measured grid -> experiments/live/
python live/analyze.py                  # experiments/live/summary.md and summary.csv
```

## Known Issues (legacy simulation path)

- The live experiments use `live/`, not `scripts/run_experiment.sh`; the launcher and the items below describe the older simulation path only.
- `src/flink_pipeline.py` is missing; the launcher's Flink path does not work.
- `src/pipeline.py` does not accept the launcher's `--trial` argument.
- No per-trial JSON output is produced, so the launcher's expected result files never exist.
- `experiments/run_simulation.py` ignores the `--input` and `--output` arguments the launcher passes.
- The aggregation step generates new simulation data instead of reading measured trial outputs.
- `experiments/statistical_analysis.csv` was removed. It had been generated by a separate script that sampled around fixed means, was not derived from the trial files, and its values did not match them.
- `experiments/cluster-results/statistical_analysis.csv`, a copy of that file, was removed for the same reason.
- `experiments/cluster-results/` contains copies of simulation outputs produced while running the scripts on an AWS EMR node. Because the scripts are seeded simulations, this shows only that they run in that environment. It is not a validation of results.
- In the simulation, Strategy C is labeled "10s WAL". Structured Streaming has no separate write-ahead-log setting; for live experiments Strategy C is redefined as a 10s trigger with RocksDB changelog checkpointing (see docs/experimental_setup.md).
